## 4. Accept 记录与限制条件

### AR-001：模块化单体

**结论：Accept。**

需求已确定 Vue、FastAPI、PostgreSQL，并只要求本机运行。多个独立后端服务没有相应的独立发布或扩容需求；单应用内按业务模块组织，更便于完成课程闭环与单库事务。

保留条件：单体必须保持模块边界，不把所有路由、查询和业务规则集中到一个文件。实际成员不足时仍需重估开发工作量，不能直接套用四人时间表。

后续动作：以 [ADR-001.md](./ADR-001.md) 记录候选比较、代价与重新评估条件。真实组内确认前状态保留 Proposed。

验证：检查模块依赖，从空库启动并完成游客、用户和管理员核心流程。

### AR-002：分层与数据所有权

**结论：Accept。**

Router 处理协议，Service 执行业务，Repository 完成查询及持久化。管理员维护景点和评价应调用已有业务服务，避免管理入口与用户入口采用不同业务规则。

保留条件：Repository 不自行提交事务；跨模块读取使用明确接口，不能直接更新别的模块拥有的实体。建议目录和接口签名不是已经存在的代码。

验证：代码评审中检查依赖方向、事务归属和重复业务校验。

### AR-003：会话与服务端权限

**结论：Accept。**

FR-AUTH-004 要求退出后当前会话失效，服务端会话便于直接撤销。NFR-SEC-002、004 要求后端执行角色和资源所有者判断；用户 ID 应来自会话，不能由客户端指定。

保留条件：8 小时有效期是设计默认，不是需求中已确认的数值。Cookie 方案需要同时落实 Origin、CSRF、HttpOnly 等约定；管理员不是普通用户权限的自动超集。

验证：旧 Cookie 在退出后不能访问受保护接口；普通用户调用后台被拒绝；用户 A 无法读写用户 B 的方案、预约或评价；错误 CSRF 被拒绝。

### AR-004：可解释规则推荐

**结论：Accept。**

FR-PLAN-003～006 要求考虑兴趣、费用、热度和距离，并尽量满足预算及开放时间。先筛掉不可行候选，再按兴趣分组和评分选择，能避免高分掩盖硬约束失败。

保留条件：贪心算法不保证全局最优；`complete` 仅表示每日至少有一项，不表示时间全部排满或路线最短。权重 0.40/0.25/0.20/0.15 为建议值，演示需记录实际配置。每日首项交通为 0 的假设必须向用户说明。

验证：固定候选、预算和时钟，检查无重复、零预算免费景点、闭馆排除、交通取整、部分方案与无方案。5 秒是性能目标，不能只凭算法复杂度宣称通过。

### AR-005：服务端草稿与幂等保存

**结论：Accept。**

客户端只提交 `preview_id` 和名称；安排、价格和快照来自服务器。消费标志、草稿行锁及来源唯一约束能够处理双击保存和网络重试。

保留条件：草稿 30 分钟是设计默认。首次保存复核日期及景点版本；已经消费的草稿优先返回原方案；原方案删除后不能被重试复活。

验证：修改客户端金额不能改变结果；并发保存同草稿只产生一个方案；删除后旧草稿返回 `PREVIEW_ALREADY_USED`。

### AR-006：历史快照

**结论：Accept。**

FR-ADM-004 要求下架后保留历史行程和预约。只保存当前景点 ID 会使改名、改价或改开放时间影响旧记录；保存必要快照能维持历史语义和重算依据。

保留条件：行程与预约使用各自的快照模型；快照含版本，不静默改用最新景点信息。当前下架诊断与冻结时间、费用分别处理。

验证：先保存记录，再修改景点和下架；旧记录仍能展示原信息，满足条件的历史预约仍可取消和评价。

### AR-007：事务及数据库防重

**结论：Accept。**

仅在接口中“先查询再插入”不能覆盖并发请求。未取消预约的部分唯一索引、评价预约 ID 唯一、父方案行锁和版本校验，是业务校验之外的完整性保护。

保留条件：业务事务保持短小；锁顺序统一；必要数据库不可用与未知错误分别处理；捕获具体约束错误，不能把所有数据库异常都解释为重复预约。

验证：在真实 PostgreSQL 测试库中检查并发重复预约、重复评价、版本冲突和故障回滚，不能仅用 SQLite 替代这些验证。

### AR-008：派生状态与一次评价

**结论：Accept。**

DEC-025 已确认按日期推导完成状态。统一规则为：先判断取消，再判断游览日期是否早于今天；今天仍为待游览，但取消只允许游览日期大于今天。

保留条件：同一次请求固定一个上海业务日期。评价只允许本人已完成且未取消的预约；用户删除采用逻辑删除，不能释放同预约再次评价资格。管理员不得恢复作者删除的评价。

验证：覆盖昨天、今天、明天的状态和动作，以及取消、隐藏、作者删除后的评价资格和评分。

### AR-009：行程调整与冲突保留

**结论：Accept。**

FR-PLAN-012 明确要求重算并保留有冲突的手工调整。因此“存在警告仍返回成功”具有需求依据，不应简单用输入错误拒绝全部调整。

保留条件：上移、下移限同一天，首末边界不可越过；重算使用冻结快照；跨午夜输出完整日期，避免只显示时间而掩盖冲突。删除最后一项保留空的已有方案，与不保存空生成结果区分。

验证：交换顺序、删除景点及产生跨日结果后，费用、预计时段、版本和警告同步更新。

### AR-010：质量措施与交付优先级

**结论：Accept。**

需求要求增长列表分页、关键逻辑自动测试和 Must 全部通过。分页、集中规则和少量核心端到端流程均能与课程验收直接关联。

保留条件：Should/Could 不被提升为本次必交能力；单页 20/100、备份演练、具体性能样本属于实现或验证建议。不能把建议测试计划写成已经测得的结果。当前没有组员，建议分工需要真实协商后确定。

验证：对应 AC-NFR-001～005 检查记录翻页、权限、回滚、浏览器与性能；报告写明实际环境、数据量和未完成项。

## 5. Reject 记录与替代建议

### AR-011：未经网络验证就固定默认导航供应商

**结论：Reject。拒绝对象是默认供应商选择，不是第三方导航能力或 MapAdapter。**

原建议：总体架构 §10 和接口 §7.1 将 Google Maps Directions 作为默认导航入口，另外提供高德位置标记。

判断依据：FR-POI-008、DEC-027 要求导航入口为 Must；NFR-REL-002 要求外部地图失败不影响核心功能。现有文档记录了 URI 方案及降级要求，但没有提供演示电脑、浏览器和网络下的实际可达性记录。因此，协议格式成立不能证明它适合作为当前项目的默认入口。本次没有实测该服务，不断言其一定可用或一定不可用。

替代建议：

1. 保留 MapAdapter，供应商选择放入统一配置。
2. 在实际演示环境验证候选地图入口，检查终点、坐标系、经纬度顺序及 URL 编码；根据结果选择默认方案。
3. 单点标注与路线导航分别标识，高德 marker 不能直接当作已完成导航功能。
4. 未验证前保留地址、坐标和复制功能，但不能因此宣称 Must 导航已经通过验收。

后续状态：待验证、待小组确认；本次未改动原四份设计文档。确认后应同步 architecture §10、api-design §7.1 和 module-design §7.3。

### AR-012：强制所有景点都支持预约

**结论：Reject。拒绝对象是“至少一个场次”的强制约束，不是场次固定词表。**

原建议：api-design §11.1 要求 `booking_slots` 至少一个场次；data-design §4.4 要求每个景点至少一条场次记录。这会使每个可保存的景点都具有预约能力。

判断依据：FR-BOOK-001 使用“可预约景点”，没有明确“所有景点均可预约”。当前约束将一个尚未确认的产品假设固化为接口校验，无法表达只提供信息、无需模拟预约的景点。评审不擅自确认一定存在此类景点，而是认为现有依据不足以强制排除它们。

替代建议：

1. 先确认是否允许不可预约景点；如果明确所有景点都模拟预约，应记录产品决定后再恢复该强制限制。
2. 如需要不可预约景点，可采用 `booking_slots=[]` 表示，无须同时增加含义重复的开关字段。
3. 空场次景点仍可浏览、收藏和推荐；界面不给预约入口，服务端也拒绝新预约。
4. 既有预约继续按快照和原日期规则处理，不因管理员后续清空场次而删除历史记录。

后续状态：需求待澄清；空数组方案只是候选修订，不是已生效规则。确认后同步 API、数据、模块文档及新预约拒绝码，增加对应测试。
