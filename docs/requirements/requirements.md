# 智游北京——需求规格说明书

> 文档状态：第一版需求基线（待技术方案确认）  
> 项目类型：高级软件工程课程项目  
> 项目周期：暂定 2 周  
> 团队规模：4 人

## 1. 项目概述

“智游北京”是一个面向北京旅游场景的响应式 Web 应用。系统通过景点信息检索、可解释的规则推荐、行程管理、模拟预约和评价等能力，帮助游客以较低的决策成本制定可执行的旅游计划；同时为管理员提供旅游资源、预约和评价管理能力。

本项目以课程演示和软件工程实践为目标，不以连接真实旅游交易平台或投入商业运营为目标。

## 2. 项目目标

1. 为游客提供集中、易用的北京景点查询入口。
2. 根据游客的日期、时间、预算和兴趣生成合理的分日行程。
3. 让用户能够保存并简单调整行程，而不必手工从零规划。
4. 以模拟预约和评价形成完整但可控的业务闭环。
5. 通过角色权限、自动化测试和可追踪需求体现软件工程质量。

## 3. 项目范围

### 3.1 范围内

- 北京单一示范城市，预置约 20～30 个景点。
- 景点浏览、关键词搜索、多条件筛选、排序和详情查看。
- 普通用户注册、登录、退出和会话管理。
- 景点收藏及收藏列表。
- 基于规则的个性化行程推荐、推荐理由展示和行程保存。
- 已保存行程的重命名、景点上移、下移、删除及整份方案删除。
- 门票模拟预约、预约查询和符合规则的预约取消。
- 基于已完成预约的评分与评论。
- 管理员对景点、预约和评价进行管理。
- 地图位置展示、第三方导航入口和基础运营统计（Should Have）。

### 3.2 范围外

- 真实支付、退款、发票、实名核验和真实票务库存。
- 酒店、机票、火车票或市内交通票务预订。
- 实时天气、实时客流、实时路况或精确路线导航。
- 社交聊天、关注关系、多人协同行程和公开分享。
- PDF 导出、日历同步、多语言和原生移动应用。
- 全国城市旅游数据平台或商业级内容运营体系。
- 用户账号管理、账号封禁、密码找回或管理员重置密码。

## 4. 用户角色

| 角色 | 说明 | 主要能力 |
| --- | --- | --- |
| 游客 | 未登录访问者 | 浏览、搜索、筛选和查看景点详情；查看公开评价 |
| 注册用户 | 已登录普通用户 | 游客能力，以及收藏、生成/管理行程、模拟预约、评价和查看个人记录 |
| 管理员 | 使用预置管理账号的运营人员 | 管理景点、查看预约、隐藏/恢复评价、查看基础统计 |

管理员账号不通过公开注册流程产生。管理员不能代替用户发起个人预约或评价。

## 5. 业务假设与约束

1. 团队由 4 人组成，开发周期暂定 2 周，需求以可演示的 MVP 为核心。
2. 系统使用小组整理并预置的北京景点数据，不承诺信息实时准确。
3. 推荐算法采用可解释的规则和加权评分，不依赖大语言模型。
4. 地图只用于位置呈现和跳转至第三方导航，不承诺实时导航能力。
5. 预约是教学用途的模拟记录，不发生真实交易和库存扣减。
6. 系统时间和日期校验以服务器配置时区为准，建议统一使用 Asia/Shanghai。
7. 前端采用 Vue，后端采用 FastAPI，数据库采用 PostgreSQL。
8. 项目只要求在本机环境完成部署和演示，不把公网部署、域名、HTTPS 证书和云资源作为本次验收内容。

## 7. 核心业务规则

### 7.1 推荐评分

推荐实现应采用可配置权重的加权评分。建议默认构成为：兴趣匹配度 40%、景点热度 25%、预算适配度 20%、距离适配度 15%。权重属于实现参数，可在不改变业务含义的情况下调整，但应在演示或技术文档中记录实际值。

- 明确不符合用户兴趣的景点仍可作为补充候选，但分数应低于匹配景点。
- 超出剩余预算、已被安排或当日明显无法游览的景点不得进入最终结果。
- 如果候选景点不足，系统可生成部分行程，但必须告知用户原因。
- 推荐理由至少应指出一个主要因素，例如“符合历史文化兴趣且票价在预算内”。
- 景点间距离采用经纬度计算直线距离；交通时间按“直线距离 ÷ 20 km/h + 15 分钟”估算，并向上取整到 5 分钟。
- 界面应明确标注交通时间为规划参考值，不代表实时路线或实际通行时间。

### 7.2 行程时间与费用

- 开始日期不得早于当天，允许从当天开始；游玩天数必须为 1～7 天的整数。
- 用户为整个行程设置一个统一的每日可用时间段；开始和结束时间适用于所有游玩日，且结束时间必须晚于开始时间。
- 每日安排不得超过用户提供的可用时间；交通时间可使用预置或估算值。
- 预计费用至少包含景点参考票价，不包含餐饮、住宿和真实交通支出。
- 每个景点按星期配置是否开放及一个开放时间段；MVP 不处理午休、多段开放时间或节假日临时调整。
- 同一天内上移、下移或删除景点后，应重新计算预计时段、交通时间和总费用。
- 手工调整产生时间冲突时允许保存，但应在相关行程日和景点上显示清晰警告。

### 7.3 预约状态

预约状态至少包括：`待游览`、`已完成`、`已取消`。

- 创建成功后状态为“待游览”。
- 游览日期结束后，系统可在查询时按日期推导为“已完成”，无需定时任务。
- 用户主动取消后状态为“已取消”。
- 已取消预约不能用于评价资格判断。
- 可选场次为“上午”“下午”“全天”；每个景点应配置自身支持的场次。
- 预约日期允许为当天至未来 90 天，边界日期均包含在内。
- “重复预约”以用户、景点、游览日期和场次共同判断，只统计未取消预约；取消原记录后可重新创建。

### 7.4 评价可见性

- 评价状态至少包括“可见”和“已隐藏”。
- 用户删除自己的评价采用逻辑删除；记录继续保留，但不得公开展示或计入平均评分。
- 管理员不得恢复用户主动删除的评价。
- 管理员隐藏评价时应保留记录，以便恢复。

### 7.5 热度与排行

- 每个景点预置一个 0～100 的基础热度，推荐评分中的热度因素使用该值。
- 管理后台热门景点分数按“收藏数 + 2 × 未取消预约数”计算，并按分数从高到低排列。
- 排行统计应排除已取消预约；同分时按基础热度从高到低排列。

## 8. 数据需求

### 8.1 核心实体

| 实体 | 关键字段示例 |
| --- | --- |
| 用户 | 用户 ID、规范化用户名、显示用户名、密码摘要、角色、创建时间、状态 |
| 景点 | 景点 ID、名称、分类、简介、图片、图片来源与许可、地址、经纬度、按星期设置的开放状态及单一时间段、建议时长、票价、标签、热度、上下架状态 |
| 收藏 | 用户 ID、景点 ID、收藏时间 |
| 行程方案 | 方案 ID、用户 ID、名称、开始日期、天数、预算、创建时间 |
| 行程项 | 方案 ID、游玩日序、景点快照/景点 ID、顺序、预计时段、预计费用、推荐理由 |
| 预约 | 预约 ID、预约编号、用户 ID、景点快照/景点 ID、日期、场次、人数、状态、创建时间 |
| 评价 | 评价 ID、用户 ID、预约 ID、景点 ID、评分、正文、可见状态、创建时间 |

### 8.2 数据完整性

- 用户名去除首尾空格后保存，并按英文字母大小写不敏感的规范化值保持唯一。
- 同一用户不能重复收藏同一景点。
- 收藏、行程方案和预约总数不设业务上限，列表接口应使用分页控制单次返回量。
- 同一预约最多对应一条有效评价。
- 方案、收藏、预约和评价必须归属于有效用户。
- 关联景点下架或修改后，历史预约和已保存行程应保留可理解的名称、日期、费用等必要信息。

### 8.3 固定分类与兴趣标签

- 景点分类：历史古迹、博物展览、自然风光、城市地标、主题乐园、文化艺术。
- 兴趣标签：历史、建筑、自然、文化、艺术、亲子、摄影、休闲、美食。
- MVP 中采用固定词表，管理员只能从词表中选择，不能自行新增分类或标签。

| NFR-SEC-003 | 安全 | 系统应对输入执行服务端校验，并使用安全的数据访问方式降低注入风险。 | Must |

| NFR-USE-001 | 易用性 | 表单应标识必填项，并对无效输入给出可理解、可定位的中文提示。 | Must |
| NFR-USE-002 | 易用性 | 加载、空数据、成功和失败状态应具有清晰反馈，避免无响应感。 | Must |
| NFR-REL-001 | 可靠性 | 创建预约、保存行程等写操作失败时，不应留下用户可见的半完成数据。 | Must |
| NFR-REL-002 | 可靠性 | 第三方地图或导航服务不可用时，景点详情、行程、预约及其他核心功能仍应可用，并给出适当提示。 | Must |
| NFR-TEST-001 | 可测试性 | 账号权限、推荐规则、预约规则和评价资格等关键逻辑应具有自动化测试。 | Must |
| NFR-MAIN-001 | 可维护性 | 推荐权重、人数范围、行程天数范围和评论长度等规则应集中配置或集中定义。 | Should |
| NFR-DATA-001 | 数据说明 | 系统应明确标注演示数据和参考价格不代表实时官方信息。 | Must |
| NFR-DATA-002 | 素材合规 | 景点图片应使用开放许可素材或小组制作的占位图，并记录来源和许可；不得使用来源不明的网络图片。 | Must |

## 10. 优先级与发布范围

### 10.1 Must Have

- 账号与权限控制。
- 景点浏览、搜索、筛选和详情。
- 收藏。
- 规则推荐、行程保存和顺序调整。
- 模拟预约及取消。
- 预约后评价及评价管理。
- 景点、预约和评价后台管理。
- 关键安全、性能、校验和测试要求。

### 10.2 Should Have

- 地图位置和第三方导航入口。
- 景点排序。
- 行程重命名和整份删除。
- 后台基础统计与排行榜。

### 10.3 Could Have

- 基于收藏历史调整推荐分数。
- 复制已有行程。
- 更丰富的后台可视化图表。

## 11. MVP 完成定义

项目可被视为达到最低交付要求，当且仅当：

1. 所有 Must Have 用户故事通过对应验收标准。
2. 游客、普通用户和管理员的核心流程可在演示环境中连续完成。
3. 普通用户不能通过页面或直接调用接口访问管理员能力或他人数据。
4. 关键业务规则具有可重复执行的自动化测试。
5. 系统包含足以演示搜索、推荐、预约和评价的北京景点种子数据。
6. 已知未完成项和限制被记录，不以“真实服务”名义展示模拟能力。
